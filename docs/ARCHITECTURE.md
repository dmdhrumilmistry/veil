# Veil architecture

## Goals

1. **No servers of our own.** Live messages, files and keys go device to device. Veil operates no infrastructure. For invite links and offline messages it can use existing **public Nostr relays** as untrusted pipes for end-to-end encrypted, padded, sender-unlinkable blobs. Users can switch that off and stay purely peer-to-peer.
2. **Defense in depth.** Do not rely on one layer (DTLS) alone. Authenticate everything. Fail closed.
3. **Small, auditable crypto surface.** Every primitive goes through `app/src/crypto/primitives.ts`. Only WebCrypto and the audited `@noble` libraries are used.
4. **Works everywhere a modern browser runs.** Installable PWA, offline app shell, responsive from 320 px phones to 4K.

## Two apps, one protocol

| | Web app (`app/`) | Native app (`flutter/app/`) |
|---|---|---|
| Protocol code | TypeScript (`app/src/crypto`, `app/src/net`) | Dart, `flutter/veil_core` (no Flutter dependency) |
| Crypto | WebCrypto + `@noble/post-quantum` | `cryptography` + `pqcrypto` (FIPS 203 ML-KEM) + `bip340` |
| Storage | IndexedDB, master key wrapped by the passphrase (PBKDF2) | SQLite, random master key in the OS keystore (Android Keystore / iOS Keychain), unlocked with biometrics or the device PIN |
| Transport | browser WebRTC, WebSocket | `flutter_webrtc`, `dart:io` WebSocket |
| History | paginated by per-chat sequence numbers | same |

**How they stay compatible:**
- `protocol/vectors.json` is generated by the web app. It contains exact outputs for ML-KEM-768, X25519/Ed25519, the handshake transcript and key schedule, live chain frames and safety numbers, plus ciphertexts the other side must open: Double Ratchet messages in both directions, envelopes, invite join notes, Nostr events, one-time codes and a backup file.
- `flutter/veil_core/test/vectors_test.dart` must reproduce or open every entry.
- `app/test/interop.test.ts` runs the TypeScript handshake against the compiled Dart one (both roles), then exchanges encrypted frames.
- CI runs all of this on every push.

**Not yet in the native app:** live file transfer. Incoming offers are declined politely, and files from restored backups can be viewed. Background notifications and deep links for `https://` invite links are also missing: paste or scan the link instead.

## Connection setup (out-of-band signaling)

WebRTC needs the two peers to swap an SDP offer and answer. Veil packs each into a **code**:

```
VEIL1O.<base64url(deflate-raw(JSON{ v, k:"offer",  sdp, id, name, ref }))>
VEIL1A.<base64url(deflate-raw(JSON{ v, k:"answer", sdp, id, name, ref }))>
```

- `id` is the sender's Ed25519 identity public key. The receiver pins the handshake to it.
- `ref` ties a reply to the invite it answers.
- ICE gathering finishes before the code is produced (no trickle), so one message per direction is enough. Codes are about 700 characters.
- Links put the code in the URL **fragment** (`#VEIL1O...`), which browsers never send to the web server. The app removes it from history immediately.
- When the inviter opens a *reply link*, it lands in a new tab. That tab forwards the code over a same-origin `BroadcastChannel` to the tab that holds the pending `RTCPeerConnection`.
- Decoding is bounded (24 KB code, 32 KB inflated) to block decompression bombs, and every field is validated.

Two **pre-negotiated** data channels share the SCTP association: `ctrl` (id 0) for chat and control, and `bulk` (id 1) for file data.

## Protocol

### Handshake (inside the DTLS channel, before any application data)

```
I → R   HELLO { v:1, id_I, eph_I, kem_pk_I, nonce_I }
R → I   HELLO { v:1, id_R, eph_R, kem_ct_R, nonce_R, sig_R }
I → R   FIN   { sig_I }

T      = SHA-256( lp("veil/v1/handshake", fp_I, fp_R,
                     id_I, eph_I, kem_pk_I, nonce_I,
                     id_R, eph_R, kem_ct_R, nonce_R) )         lp = length-prefixed
sig_R  = Ed25519_R("veil/v1/sig/R" || T)
sig_I  = Ed25519_I("veil/v1/sig/I" || T)
ss     = X25519(eph_I, eph_R) || ML-KEM-768.Decaps(kem_ct_R)
okm    = HKDF-SHA-256(ikm = ss, salt = T, info = "veil/v1/chains", L = 128)
       = ctrl_I→R || ctrl_R→I || bulk_I→R || bulk_R→I
```

- `fp_I` and `fp_R` are the DTLS certificate fingerprints each side saw in the SDP. If the signaling was tampered with, the two sides compute different `T` and the signatures fail.
- The responder keeps its keys **pending** until FIN proves the initiator holds its identity key.
- Wrong version, wrong field lengths, invalid ML-KEM keys, all-zero X25519 output, an unexpected message order, or a peer that presents our own key all abort the handshake.
- The handshake has a 20 s timeout.

### Records

For each direction and channel there is a KDF chain:

```
mk_n   = HMAC-SHA-256(ck_n, 0x01)
ck_n+1 = HMAC-SHA-256(ck_n, 0x02)        ck_n is wiped
frame  = seq_n (u64 BE) || AES-256-GCM(key = mk_n, iv = 0^32 || seq_n, aad = label || seq_n, pt)
```

- Data channels are reliable and ordered, so the receiver requires `seq == expected`. A gap, replay or reorder kills the session.
- Labels (`veil/v1/ctrl`, `veil/v1/bulk`) stop frames from being moved across channels.
- `ctrl` plaintext is JSON. `bulk` plaintext is `fileId(16) || index(u32) || bytes`.

### Application messages (`ctrl`)

`profile`, `msg`, `receipt` (delivered/read), `typing`, `disappear`, `file-offer`, `file-accept`, `file-decline`, `file-cancel`, `file-done`. Every field is type- and length-checked. Unknown types are ignored, for forward compatibility.

### File transfer

1. Sender → `file-offer { fileId, name, size, mime }`. The receiver auto-accepts up to a configurable size (default 25 MB) or asks the user.
2. On `file-accept`, the sender streams the file. It reads 1 MiB blocks, hashes them (SHA-256), seals a local copy, and sends `bulk` frames of about 64 KiB. Sends are pipelined and bounded by an 8 MiB buffered-amount high-water mark (resuming at 1 MiB).
3. The receiver checks frame order and the announced size, hashes the data incrementally, and buffers it into 1 MiB blocks sealed into IndexedDB. Awaiting storage applies natural backpressure.
4. `file-done { sha256, size }`. The receiver waits for the bulk stream to catch up, then verifies the digest. On a mismatch the data is discarded.

## Storage

```
meta/vault  = { kdf: PBKDF2-SHA-256, iter: 600000, salt, iv, wrapped = AES-GCM(KEK, master, aad="veil/vault/v1/wrap") }
master ─HKDF→ recordKey (AES-256-GCM, non-extractable) + indexKey (HMAC)

kv/identity                    sealed { Ed25519 pub, PKCS#8 }
kv/profile, kv/settings        sealed JSON
kv/contact/<HMAC(contact id)>  sealed contact
msgs/<HMAC(chat)>/<msgId>      sealed message
chunks/<HMAC(file)>/<index>    sealed 1 MiB file block
```

Every record has a fresh 96-bit IV and uses its slot name as AAD, so records cannot be swapped. Changing the passphrase re-wraps the master key without re-encrypting data. Locking (manual, idle timeout, or `pagehide`) closes sessions, drops all keys and revokes object URLs.

## Offline messages over public Nostr relays

```
 Alice                                   public relays (nos.lol, primal, ...)            Bob
 ─────                                   ─────────────────────────────────            ───
 DR-encrypt(msg) → padded envelope
 → gift wrap: kind 1059, throwaway key,  ──►  stores event until it expires   ──►  live subscription
   ["p", Bob's mailbox key], expiry           (sees ciphertext only)               (#p = his mailbox key)
                                                                                    trial-decrypts, DR-decrypts
```

**Mailbox key:** every user gets a random secp256k1 key at first unlock. It is unrelated to the identity key and is only shared with contacts. The relays a user reads are listed in Settings, 4 defaults and up to 6, `wss://` only.

**Setup (during any live session):**
1. The handshake HKDF output is extended by 32 bytes: `asyncRoot`. This is prefix-compatible, so the existing chain keys are unchanged.
2. Both sides derive `SK = HKDF(asyncRoot, "veil/v1/ratchet/sk")` and `envKey = HKDF(asyncRoot, "veil/v1/mailbox/env")`. `asyncRoot` is then wiped.
3. The responder sends `ratchet-init { pub }`. The initiator runs `RatchetInitAlice(SK, pub)` and answers `ratchet-hello`. The responder runs `RatchetInitBob`. Associated data is `veil/v1/ratchet/ad || id_I || id_R`.
4. Each side sends its mailbox card `{ pk, relays }`.

Every live session re-seeds a new **epoch**. The previous epoch is kept so messages already in flight still decrypt (2 epochs max).

**Sending while the contact is offline:**
- **What can go offline:** `msg`, `receipt`, `profile`, `disappear`, `mailbox` and `rtc` messages.
- **Encryption and wrapping:** the message is encrypted with the newest epoch's ratchet, and the state is persisted *before* publishing. It is sealed in a padded envelope (`iv || AES-256-GCM(envKey, pad(len || dr_message))`, buckets of 1/4/16/48 KiB), base64url-encoded into a NIP-59-style gift wrap and published to the contact's relays.
- **Wrapper:** kind 1059, signed by a fresh random key per event, `["p", recipient mailbox key]`, NIP-40 `expiration` (30 days for mail, 1 hour for signaling), with `created_at` randomly backdated by up to 60 seconds.
- **If no relay accepts it,** the signed event waits in an encrypted outbox and is re-published unchanged. The same id means receivers never see duplicates.
- **Files and typing indicators** always need a live session.

**Receiving:**
- One WebSocket subscription per relay (`{ kinds: [1059], "#p": [myPk], since }`) delivers events in real time while Veil is open, and catches up on unlock.
- Events are signature-checked, deduplicated across relays, and remembered (the last 3,000 ids, persisted) so relays replaying history cost nothing.
- Envelopes have no sender id, so they are trial-decrypted against each contact's envelope keys, then pending invite channels, then active invites.

**What relays learn:**
- Relays see an opaque mailbox key receiving padded blobs from unlinkable throwaway keys, plus timing and IP addresses.
- They never see content, sender identity, ratchet headers, counters, contact lists or names.
- Ciphertext may outlive its expiry on relays that ignore NIP-40, but per-message ratchet keys are deleted after use, so old ciphertext stays useless.

**Never in backups:** ratchet state and the mailbox key. Restoring an old ratchet would reuse keys. A restored device gets a new mailbox key and re-establishes offline messaging at the next live connection.

**Validation:** peers can only point us at `wss://` relays (`ws://localhost` only when the app itself runs locally), at most 6, and mailbox keys must be 32-byte hex. Publishing to a contact's relays uses temporary, publish-only connections that never subscribe, so our own mailbox key is not revealed there.

## Invite links and one-tap reconnect (rendezvous)

Manual codes are WebRTC offers tied to a live `RTCPeerConnection`, so they die when the inviter's tab closes or locks, and both people must be online together. With public relays on (the default), signaling travels through them instead.

**Invite links (v3):** `#VEIL3I.<deflate(JSON{ v:3, id, name, mb, rl, ik, tok, iid, exp })>`, about 370 characters.
- `mb`/`rl` are the inviter's mailbox key and relays. `ik` is an X25519 key made for this invite, and `tok` is a 128-bit secret.
- `exp` defaults to 7 days (1 to 30 configurable). The inviter keeps `ik`'s private key and `tok` in the vault and can revoke them.
- The joiner publishes a sealed `join` note to the inviter's mailbox: `epk || envelope(k_join, { iid, tok, id, name, reply: joiner's card, aid, ts })` with `(k_join || k_chan) = HKDF(X25519(epk, ik), salt = iid, "veil/v1/invite")`.
- The inviter checks `tok` in constant time, **claims** the invite for the first joiner's identity (single use), and starts signaling over `k_chan`.
- Links from v0.7 (`VEIL2I`, self-hosted relay) are rejected with a clear message.
- **Interception detection:** a used invite is kept as a *spent* record until it expires. If a different identity later presents it, either the link was shared twice or someone intercepted it and joined first. Veil then:
  - tells that joiner over their private join channel ("already used by someone else"),
  - adds a warning to the chat with whoever claimed it, raises an alert, and flags the invite in Settings,
  - asks the user to compare safety numbers with that contact.
  The `invite-used` notice is sealed with that joiner's `k_chan`, so only the real inviter can send it.

**Signaling:** three messages, `{ t: "rtc", k: "knock" | "offer" | "answer", aid, ts, sdp? }`.
- Between contacts they travel **inside the Double Ratchet**, so they are authenticated as that contact. Over an invite they are sealed with `k_chan`.
- Knocks are valid for 3 minutes and offers for 90 seconds. A stale offer makes the side that still wants to connect knock again, so the devices meet whenever both are online.
- Glare (both knock or both offer) is resolved by identity order: the smaller key offers.
- Relay subscriptions are live, so the whole exchange usually completes in a second or two.
- The resulting live session runs the normal hybrid post-quantum handshake with `expectedPeer` pinned to the identity from the invite or contact. A relay that tampers with signaling only causes a failed connection.

**Verification is the last step to "only the two of you":** encryption guarantees that only the two devices that ran the handshake can read a chat. Safety numbers prove the other device is the person you meant (no one swapped themselves in when you first connected). Unverified chats show a "Not verified yet" bar. Verifying is one tap: scan the safety QR on the other person's screen (BarcodeDetector). A match marks the contact verified, and a mismatch raises an interception warning. Browsers without a camera scanner compare the 60 digits manually.

**Auto-connect (setting, on by default):** opening a chat with an offline contact sends one knock (at most every 5 minutes), and incoming knocks are answered automatically. Turning it off stops your device from revealing that you are online. Knocks are then answered only while you have that chat open, and otherwise logged as "tried to connect".

**Manual codes are still there** (relays off, or both people together). They no longer auto-lock while waiting, hold a screen wake lock, and expire explicitly after 15 minutes with a clear message.

## Encrypted backups

A backup is one portable `.veilbackup` file (see `app/src/storage/backup.ts`):

```
file      = "VEILBAK\x01" || u32 headerLen || header JSON { v: 1, kdf: "PBKDF2-SHA-256", iter: 600000, salt }
key       = HKDF-SHA-256(PBKDF2(passphrase, salt, iter), salt = SHA-256(magic || headerLen || header), "veil/backup/v1")
record    = u32 len || iv(12) || AES-256-GCM(key, iv, type || payload, aad = u64 index || final)
types     = 0x01 JSON entry { k, d } | 0x02 file chunk (fileId, index, bytes) | 0xFF end { records }
```

- The backup passphrase is independent of the device passphrase, so a backup can be restored after the device passphrase is forgotten.
- Hashing the header into the key detects header edits (a wrong key results). Record indexes and the final flag in the AAD detect reordering, splicing, dropped records, trailing data and truncation. A valid file ends with exactly one authenticated end record.
- Contents: the identity key (PKCS#8), profile, settings, contacts, non-expired messages, and optionally file chunks. Files left out are marked "not included in backup". Unread counts, `lastBackupAt` and notification permission are reset on restore.
- Writing streams straight to disk with the File System Access API where available. Otherwise it builds a Blob for download.
- **Restore** first decrypts and authenticates the whole file without writing anything, then shows a summary. Only after the user confirms does it wipe the device, create a new vault (with the backup passphrase or a new one), and re-encrypt every record under fresh device keys. If anything fails midway, the partial data is wiped. In-flight transfers come back as failed.
- Restore is offered on first launch, on the lock screen ("Forgot passphrase?") and in Settings.

## Windows, installed app and updates

- **Shared storage (Android, desktop):** the installed app and browser tabs on the same origin share one IndexedDB. Each window keeps decrypted state and live WebRTC sessions in memory, so only **one window is active at a time**, enforced with the Web Locks API (`app/src/state/instance.ts`). A second window shows "Veil is open in another window - Use Veil here". Taking over `steal`s the lock, and the previous window tears down its sessions and keys. Neither window ever runs on a stale copy of the data.
- **Separate storage (iOS/iPadOS):** Home Screen apps get storage isolated from Safari, so they are independent installations with different identities. Data moves between them with an encrypted backup and restore. The app explains this on iOS during install and first run.
- **Updates:** the service worker is versioned per build. Open windows check for a new version hourly and whenever they become visible. If an update lands during a conversation, a "Reload" banner appears instead of interrupting. Otherwise the app reloads itself.

## Notifications

Web Push would need a server we run, holding your push subscription and waking your device, which also reveals when you get messages. Veil has none, so notifications are **local**. The running app raises them when a message, file or connection arrives while Veil is in the background. That includes offline mail arriving over the live relay subscription. Messages sent while Veil is fully closed wait on the relays and show up the next time you open it.

- Shown through the service worker (`registration.showNotification`). Android browsers and installed iOS apps reject `new Notification()`. On iOS/iPadOS, notifications require Veil to be added to the Home Screen.
- **Never** includes message text. The sender's name is opt-in (`Show who it is from`), since it appears on lock screens.
- One notification per conversation (`tag`). Newer messages replace it with a count and vibrate again (`renotify`).
- The payload carries a random in-memory token, not a contact id. Tapping the notification focuses Veil and opens that chat (`notificationclick` → `postMessage`). Tokens are forgotten on lock.
- Opening a chat or returning to the app clears its notifications. The unread total shows in the tab title and as an app-icon badge (Badging API, installed apps).
- While Veil is visible but you are in another chat, an in-app toast appears instead.
- Limits: phones suspend background web apps after a while (iOS within minutes), which drops the connection, and auto-lock disconnects on purpose.

## Web platform hardening

- CSP (meta tag, since GitHub Pages cannot set headers): `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' blob: data:; media-src 'self' blob:; connect-src 'self' wss: ws://localhost:* ws://127.0.0.1:*; worker-src 'self'; base-uri 'none'; form-action 'none'; object-src 'none'; require-trusted-types-for 'script'; trusted-types veil-sw`.
- `connect-src` allows `wss:` because users choose their public relays. No `https:` or other origins are reachable. Script execution stays locked to `'self'` with Trusted Types, so this does not widen what code can run.
- One Trusted Types policy, which only allows the service worker URL `./sw.js`.
- `referrer: no-referrer`. No external fonts, images or scripts.
- The service worker caches only same-origin GET requests for the app shell. Navigation is network-first so updates land quickly.
- Dependencies are pinned exactly and the lockfile is committed. CI runs `npm audit`, typecheck, unit tests, a build and a two-browser E2E test. GitHub Actions are pinned by commit SHA, and Dependabot keeps them current.

## Testing

- `app/test/crypto.test.ts` covers handshake correctness, DTLS-fingerprint MITM detection, identity pinning, tampered hello, forged FIN, version and junk rejection, chain replay/reorder/tamper/cross-channel rejection, and safety number symmetry.
- `app/test/ratchet.test.ts`, `invite.test.ts`, `nostr.test.ts` and `backup.test.ts` cover the Double Ratchet (out-of-order, replay, tamper, skip limits, persistence), invite sealing and claiming, Nostr event signing and verification, relay URL rules, and the backup format.
- `app/e2e/two-peers.mjs` covers four isolated browser profiles and an in-process Nostr relay:
  - onboarding, copy/paste signaling and a real WebRTC connection
  - messages and read receipts, and notifications
  - a multi-MB file with a byte-exact download
  - matching safety numbers, and lock/unlock with a wrong passphrase
  - backup and restore onto a new device, and single-window handover
  - offline messages with receipts and replies, one-tap reconnect, and an invite link accepted while the inviter was offline
  - scans of IndexedDB and the relay for plaintext, a check that every relay event has its own signing key, and zero console or CSP errors
- `npm run test:e2e:public` runs the same scenarios over real public relays. It is manual, not part of CI.

## Roadmap ideas

- Voice and video calls (renegotiated over the existing authenticated channel)
- Offline delivery of small files over relays (chunked, size-capped)
- Optional Tor / proxy support for relay connections to hide IP addresses from relays
- Post-quantum ratchet steps (SPQR-style ML-KEM ratchet) for post-compromise security against quantum attackers
- Group chats (pairwise sessions or MLS)
- Resumable transfers
- Encrypted backup/export between your own devices
